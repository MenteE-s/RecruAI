The P0 blockers — 2 fixed in code, 1 partial, 2 product decisions

  • Video is dead in production. Both production frontend configs (Vercel and nginx) send camera=(), microphone=(); the AWS stack has no LiveKit service and the deploy job sets no LiveKit keys.
  • Billing is a facade. POST /api/subscription/upgrade grants paid access for free, and an expired user can reset the trial indefinitely. The pricing page advertises $15/month and a 14-day trial; the app gives 30 days.
  • No password reset. Had no forgot-password route or UI; a forgotten password was a permanent support ticket. Fixed in code
  • Org invites create unreachable accounts. The API creates a user with a random password that is never sent, sends no email, and blocks that address from registering later. Fixed in code
  • Deploys now have a real test gate. Backend pytest (44 tests against PostgreSQL + pgvector) and frontend Jest (37 tests) run in CI, the production dependency audit is clean, and deploy depends on validate. Staging Playwright E2E and GitHub required-check enforcement remain production checklist items.

What is already strong

  • No live API keys are tracked in git; .env files are ignored and excluded from the Docker build context.
  • JWT revocation via Redis, verified-email blueprint guard, login lockout, OTP hashing, CORS allow-list, and tenant checks on the sensitive routes we re-tested.
  • Single Alembic head; local DB is at head; migrations run before the API starts.
  • Uploads are extension + magic-byte validated and served as non-executable images.
  • Clean module boundaries: 59 models, auth/org/ind/profile/interviews split, reusable guards and sanitizers.
  • AWS deployment is automated end-to-end with TLS, health checks, and encrypted secrets injection.

P1-02 JWT lives in localStorage, sessions die after 2 hours, and Vercel enforces no CSP Was: localStorage bearer token, 2-hour expiry, no refresh, no CSP. Now: 15-minute memory token + rotating HttpOnly refresh session and enforced CSP. P1FixedSecurity1–2 days

Why it matters

A bearer token readable by JavaScript turns any injected script, malicious dependency, or DOM sink into a 2-hour account takeover. In production the token is header-only, so the usual CSRF argument for localStorage does not apply — an HttpOnly, Secure, SameSite cookie is strictly safer. Separately, a hard 2-hour expiry with no refresh means every user is ejected twice a day, which reads as instability.

Fix

  • Move to short-lived access tokens (10–15 min) plus a rotating refresh token in an HttpOnly/Secure/SameSite=Lax cookie; add /auth/refresh and reuse detection.
  • Ship a CSP on Vercel (default-src 'self', explicit connect-src to the API/WSS, no unsafe-inline in production) and test with Report-Only first.
  • Add Permissions-Policy that allows camera/mic for self (see P0-01).
  • If cookies are out of scope, document the XSS risk and add strict CSP + dependency pinning as a compensating control.

The frontend uses a single-flight refresh, retries one 401, refreshes inside the Socket.IO auth callback, and redirects on session expiry. 06A · Runtime & scaling detail

API, workers, Redis, and Kafka are four different problems

Right now they are one process, one Redis, and one Kafka broker. That is acceptable for a demo and dangerous for production: a slow AI call can block a web thread, an evicted Redis key can un-revoke a token, and a consumer crash can lose an event. The target separates request handling from background work and separates cache from security state.

What is wrong today (evidence)
  • Kafka consumer runs inside gunicorn — app.py:145–152 starts a daemon thread per API process; kafka_consumer.py:22 uses enable.auto.commit=True, has no retry/DLQ, and broadcasts to Socket.IO from that thread.
  • Notifications are written inline — api/org/posts.py:165 and mentorship/nudges.py:70 create rows during the request; email/OTP paths are synchronous too. A slow provider becomes a slow API.
  • Redis is one 128 MB allkeys-lru instance — it holds the JWT blocklist, rate-limit counters, and cache. Eviction can make a revoked token valid again; cache.py:192 silently swallows failed revocation writes.
  • No general async worker or outbox yet — the dedicated scheduler worker now owns timed jobs (trial expiry, interview completion, purge, nudges), but email/invite delivery and notifications are still inline, and there is no retryable outbox.
  • Socket.IO has no Redis message queue — extensions.py:17 uses async_mode="threading"; with -w 1 --threads 4, long-lived sockets can exhaust the 4 request slots, and a second API replica cannot reach users connected to the first.
  • No outbox — Kafka publishes are best-effort; if the broker is down, the HTTP request succeeds but the event is gone. There is no idempotency key or replay path.

Failure behavior to decide now
  • Security Redis down: JWT blocklist reads currently raise, so auth fails closed — good, but login is unavailable. Add a replica/Sentinel or accept a short 503 with an alert.
  • Revocation write fails: block_jti currently swallows the error. Queue the revocation in the DB/outbox and retry; never silently pass.
  • Cache Redis down: serve uncached, log, alert; do not fail the request.
  • Queue Redis down: API should still commit the domain row + outbox; the relay retries. Do not make user actions depend on broker availability.
  • Rate-limit storage down: fail-open for reads, fail-closed for auth/OTP/AI, and alert.
Redis operating rules
  • Use ACLs: app user gets +@read +@write +@keyspace, not +@admin; block FLUSHALL/CONFIG.
  • Key prefix + TTL on every write; blocklist TTL ≥ max access-token lifetime (currently 2h).
  • Connection pool 20 per process; 3 workers = 60 connections; alert at 70% of maxclients.
  • Monitor evicted_keys, used_memory, blocked_clients, latency, rejected_connections.
  • Never use KEYS in request paths; replace with SCAN (P2-04).
  • AOF/RDB is not a database backup; jobs must be replayable from the outbox.

Kafka: keep it on the event log, not the request path

Kafka is a durable, replayable log — not a task queue. Use it for domain events and analytics; use Redis/Celery for “do this job now.” The current setup does neither cleanly: one partition, replication factor 1, auto-commit, and the consumer lives inside the web process.

2 brokers or 3? Neither — 3 for HA, 1 for a deliberate launch trade-off Two brokers cannot give Kafka both durability and availability. With RF=2 and min.insync.replicas=2, one broker down stops writes; with RF=2 and min.insync.replicas=1, the surviving broker can be elected leader without the latest records, so acknowledged writes can be lost. A 3-broker cluster with RF=3, min.insync.replicas=2, and acks=all tolerates one broker failure. The KRaft controller quorum also wants 3 nodes for a resilient majority. Current production is 1 broker, RF=1 — acceptable only if Kafka is non-critical and events can be rebuilt from an outbox. If Kafka matters, use 3 brokers or managed MSK; do not use 2 as an “HA” compromise.

Non-negotiable job rules
  • At-least-once + idempotency. Every task is safe to run twice; enforce with a unique key in the DB, not hope.
  • Pass IDs, not objects. Reload the row in the worker, re-check tenant scope and permissions, and never pass secrets or full PII payloads.
  • Late acks. acks_late=True, task_reject_on_worker_lost=True, prefetch_multiplier=1 for long AI jobs; a killed worker should not lose the job.
  • Bounded work. Soft/hard time limits, max retries with exponential backoff + jitter, and a DLQ after exhaustion.
  • Budget gate. Check plan/AI allowance before the call, record usage after, and fail with a user-visible message rather than silently overspending.
  • Graceful shutdown. Warm shutdown, finish in-flight work, requeue unacked jobs; deploy should not orphan tasks.
  • Observability. Queue depth, job duration, failure rate, retries, DLQ depth, worker memory; alert on age of oldest job, not just count.
  • No request-scoped Flask state. Workers create their own app context; no g, no request, no current user.

Implementation order for the worker/runtime layer

If you only have one day for runtime work Do the Redis split/policy fix, move email/OTP to a worker, and disable the in-process Kafka consumer. Those three remove the scariest failure modes. Keep one API replica so Socket.IO fan-out is still local, and schedule the outbox + Redis adapter for the first post-launch week. Do not run multiple API replicas with the current socket setup.
Scaling rules to put in the runbook No background work in the API. No in-process consumer. No allkeys-lru on security state. No unbounded queue. No synchronous AI or email in a request. Every job idempotent. Every queue has a DLQ and an age alert. Every service stateless except Postgres, Redis, Kafka, and S3. Scale the API and workers independently; add a broker only when the DB-backed queue is the bottleneck.
